# 手繋ぎの最終台車位置 (人と横並びにする)

`solve_palm_ik.py` (と同じ処理を呼ぶ `run_camera_pipeline_test.py`) が
決める最終の台車位置についての仕様と、その決め方を比較した結果を
まとめる (2026-09-28)。

## 1. 問題: 最終位置が人の前に出る

以前は、最終の台車位置が人の立ち位置より 0.3〜0.9 m 前 (人の正面方向)
に出ていた。ロボットは人と同じ向きを向くので、終点で人がロボットの斜め
後ろに来る (後述の方位で 120〜160 度)。螺旋の接近 (`plan_handshake_
motion.py`) の自転が人に背を向けて終わる、最短の回り方が逆向きになる
(human_028) といった問題も、これが原因だった。

IK は人物を (3, 0) へ平行移動したうえで、台車の可動域 `base_limits` を
人ごとに次のように絞っている。

| 軸 | 制限 | 実装 |
|---|---|---|
| x (前後) | 人の前後 ±3 m。実質無制限 | `DEFAULT_BASE_X_RANGE` |
| y (左右) | 差し出した手の側だけ | `restrict_base_y_range_to_hand_side` |
| yaw | 人の正面方向 ±30° | `restrict_base_yaw_range_to_human_facing` |

収束して干渉検証を通った候補の中からは、関節の曲げ量コストが最小のもの
を採用する (`pick_verified_candidate`)。人は手を体の 0.4〜0.5 m 前に
差し出しているので、腕を体の横に下ろしたまま繋げる位置、つまり台車が
手の真横まで前に出る解が最も安い。前後位置を縛るものが無かったので、
自然に前へずれていた。

## 2. 現在の仕様

次の 3 つを併用する。

- **x の窓 (案A)**: 台車の x を人の立ち位置 ±0.15 m に絞って解く
  (`restrict_base_x_range_to_human_standing`)。後処理 (押し込み・視線
  IK) まで通る解が無ければ、±0.3 m → 無制限と窓を広げて解き直す
  (`solve_person_ik_side_by_side`、`--base-x-standing-margins`、既定
  `0.15 0.3 -1`、負の値は無制限)。どの窓でも後処理まで通らなければ、
  最初に干渉検証を通った解を後処理なしで使う。解けた窓は結果 JSON の
  `base_x_standing_margin` に記録する。
- **前後ずれのコスト (案B)**: 候補の並べ替えを「曲げ量コスト +
  `--front-offset-weight` (既定 30) × |前方ずれ|」にする
  (`pick_verified_candidate` の `front_offset_weight`)。前方ずれは、台車
  が人の立ち位置から**人の正面方向に**どれだけ前にあるか [m]。

- **向きのコスト**: さらに「`--facing-yaw-weight` (既定 30) × |台車の
  向きの人の正面方向からのずれ| [rad]」も足す (`pick_verified_candidate`
  の `facing_yaw_weight`)。4節参照。

窓だけだと、曲げ量コスト最小の解は窓の前端 (+0.15 m) に張り付く。また
窓は world の x で取っているので、人が斜めを向いている分 (合成データでは
±25°) は、人の正面方向の前方ずれが残る。コストは人の向きに沿って測るので、
窓の中で横並びに近い候補を優先させられる。一方、コストは並べ替えるだけ
なので、前に出た候補しか収束しなかった人には効かない。窓で候補を立ち位置
付近に集め、コストでその中から選ぶ、という役割分担になる。

x の窓は、人がほぼ ±x を向いていることを前提にする (y の制限が world の
y で左右を判定しているのと同じ前提)。

`base_limits` はバッチ IK に trace 対象の引数として渡る
([`jax_compilation_cache.md`](jax_compilation_cache.md) 9節) ので、窓を
広げて解き直しても再コンパイルは起きない。

## 3. 比較

### 方法

[`jax_compilation_cache.md`](jax_compilation_cache.md) 9・11節と同じ合成
データで比べた。`--plan-motion` は付けていない。

```bash
python3 scripts/run_pipeline_test.py 100 --seed 0 [オプション]
python3 scripts/run_pipeline_test.py 200 --seed 1 [オプション]
python3 tools/summarize_final_base_placement.py <seed 0 の作業ディレクトリ> <seed 1 の作業ディレクトリ>
```

2 回分の IK 対象は計 42 人。`--seed` が同じなら骨格は同一なので、条件間
で同じ人同士を比べている。

指標の定義 (`tools/summarize_final_base_placement.py`):

- **方位**: ロボットの台車 (base_link) の中心から、人の立ち位置 (左右の
  腰の中点) を見た方向。ロボットの正面を 0 度、左回りを正とする。±90 度
  が真横で、|方位| が 90 度より大きいほど人がロボットの斜め後ろにいる。
  「|方位| ≤ 110°」は、真横から後ろへ 20 度以内 (ほぼ横並び) の人数。
  ロボットの yaw は人の向き ±30° の範囲で動くので、同じ位置でも向き
  次第で値が変わる。
- **前方ずれ**: 上記の、人の正面方向に沿った台車の前後位置 [m]。横並び
  かどうかを直接表すのはこちら。
- **IK 計算時間**: 結果 JSON の `collision_ik_time` +
  `candidate_selection_time` (IK 1段階目+2段階目、warmup は含まない)。

### 結果

| | 後処理まで成功 | 前方ずれ \|平均\| | \|方位\| 中央値 | \|方位\| ≤ 110° | IK 時間 平均 / 最大 |
|---|---|---|---|---|---|
| 修正前 | 40 (95.2%) | 0.52 m | 124° | 9/40 | 0.17 / 0.23 秒 |
| 窓 ±0.10 m 固定 | 34 (81.0%) | - | 115° | - | - |
| 窓 ±0.15 m 固定 | 36 (85.7%) | - | 115° | - | - |
| 窓 ±0.20 m 固定 | 36 (85.7%) | - | 119° | - | - |
| 案A (窓 0.15 → 0.3 → 無制限) | 41 (97.6%) | 0.25 m | 115° | 16/42 | 0.24 / 0.92 秒 |
| 案B のみ w=1 | 40 (95.2%) | 0.48 m | 129° | 8/40 | - |
| 案B のみ w=3 | 40 (95.2%) | 0.38 m | 123° | 14/40 | - |
| 案B のみ w=10 | 40 (95.2%) | 0.25 m | 112° | 20/40 | - |
| 案B のみ w=30 | 40 (95.2%) | 0.23 m | 110° | 20/40 | 0.24 / 0.80 秒 |
| 案A + 案B w=10 | 41 (97.6%) | 0.20 m | 117° | 15/42 | 0.27 / 0.93 秒 |
| **案A + 案B w=30** (4節の向きのコストの前) | **41 (97.6%)** | **0.18 m** | 113° | 20/42 | 0.29 / 0.93 秒 |

(「-」は計測していない。固定窓の成功数は solved の人数で、この時点では
後処理まで成功した人数と同じだった。)

- **窓を固定すると成功率が 90% を切る。** 解けなかったのは、修正前に
  0.6〜0.9 m 前に出ていた人たち。段階的に広げると修正前より 1 人多く
  解けた。42 人中 35 人が ±0.15 m、4 人が ±0.3 m、3 人が無制限で解けた。
- **案B は w を上げるほど横並びに近づく**が、成功率は変わらない (並べ
  替えるだけなので)。
- **併用 (w=30) は前方ずれが最小で、成功率も案A と同じ。** |方位| の
  中央値だけは案B 単独の方が少し良いが、これはロボットの yaw の違いに
  よる (上記の指標の定義を参照)。
- **最悪ケースは残る。** 窓を無制限まで広げてやっと解けた 3 人は、前方
  ずれが最大 0.92 m のまま。±0.3 と無制限の間に段 (例えば ±0.5) を
  挟むと改善する可能性があるが、試していない。
- **計算時間の最大は 0.23 → 0.93 秒に増える。** ほとんどが 2段階目の
  後処理判定。案A は、干渉検証を通っても後処理に全部失敗すると窓を広げて
  解き直す。案B は、腕を前へ伸ばす (後処理に失敗しやすい) 候補を先に調べる。
  抑えたい場合は `--post-process-max-candidates` で後処理を試す候補数に
  上限を付けられるが、成功率とのトレードオフになる (未計測)。

## 4. ロボットの向き (人の方へ斜めを向く)

実機で、横並びにはなったがロボットが人の方へ斜めを向く、という報告が
あった。yaw は人の正面方向 ±30° の窓で絞っているだけで、窓の中では縛る
ものが無い。上記の既定 (案A + 案B w=30) では 42 人中 13 人が窓の端
(人の側へ 30° が 6 人、反対側へ 30° が 7 人) に張り付いていた。

そこで、案B と同じく候補の並べ替えに向きのずれのコストを足した。並べ
替えるだけなので成功率は変わらない (全条件で後処理まで成功 41/42)。
3節と同じ方法で、案A + 案B w=30 に足して比べた。「向きのずれ」は台車の
向きの人の正面方向からのずれで、人のいる側へ回っている向きを正にする
(`tools/summarize_final_base_placement.py`)。

| `--facing-yaw-weight` | 向きのずれ \|ずれ\| ≤ 10° | \|方位\| 中央値 | \|方位\| ≤ 110° | 前方ずれ \|平均\| | IK 時間 平均 / 最大 |
|---|---|---|---|---|---|
| 0 (以前の既定) | 15/42 | 113° | 20/42 | 0.18 m | 0.29 / 0.93 秒 |
| 3 | 29/42 | 100° | 25/42 | 0.18 m | 0.28 / 0.95 秒 |
| 10 | 33/42 | 102° | 26/42 | 0.19 m | 0.26 / 0.90 秒 |
| **30 (既定)** | **37/42** | 103° | 26/42 | 0.22 m | 0.24 / 0.84 秒 |

- 向きがそろうと、方位も真横 (90°) に近づく。
- 重みを上げると前方ずれが少し増える (0.18 → 0.22 m)。向きを人に合わせた
  まま手に届く位置が、少し前になるため。
- 残る 5 人は、向きのずれが最大で +30° (窓の端) のまま。その向きの候補
  しか後処理まで通らなかったと考えられる。
