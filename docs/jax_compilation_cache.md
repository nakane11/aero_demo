# jax / jaxls のコンパイル・キャッシュ仕様まとめ

`solve_palm_ik.py`(バッチ IK)と `plan_handshake_motion.py`(jaxls の軌道
最適化)は、どちらも jax の JIT コンパイルに依存しており、初回コンパイルは
数秒〜数十秒かかる。この文書は、そのコンパイル・永続キャッシュまわりで
これまでの調査から分かった仕様・既知の問題・対策をまとめる。README.md の
「環境構築」からはリンクのみを残し、詳細はこちらに集約する。

## 1. 永続コンパイルキャッシュの基本

`solve_palm_ik.py` は起動時に jax の永続コンパイルキャッシュ(既定で
`~/.cache/jax_compilation_cache`、`JAX_COMPILATION_CACHE_DIR` 環境変数で
変更できる)を有効にする。干渉回避付きバッチ IK / jaxls の軌道最適化の
JIT コンパイルは、計算グラフの形状(`--collision-ik-stop`/
`--attempts-per-pose`/`--skeleton-dir` の有無/使う腕(`--robot-arm`)などで
決まる)ごとに初回だけ必要な重い処理(数分〜十数十秒かかることがある)で、
以降は同じ venv/jax バージョンで同じ形状の計算であればディスクキャッシュ
から即座に読み込まれる。

キャッシュのキー(フィンガープリント)はコンパイル前 HLO から決まる。
**ソースの行番号や空白などは HLO に含まれるがキャッシュキーには影響しない**
(スクリプトを編集してもキャッシュは効き続けることを確認済み)。一方、
jaxls が計算グラフに**定数として焼き込む値**(ロボットの姿勢由来の FK
パラメータなど)が 1 bit でも違うと別計算とみなされ再コンパイルになる。
詳細は「4. 既知だったキャッシュミスの原因と対策」を参照。

## 2. warmup とキャッシュの単位(腕ごとに別キャッシュ)

起動時のウォームアップ(`run_camera_pipeline_test.py` の `_warmup_ik`)は、
左右それぞれの腕で IK(`solve_person_ik`)だけでなく `plan_person_motion`
(jaxls の軌道最適化)もダミー目標に対して 1 回ずつ解いておき、JAX/jaxls
の初回コンパイルを前倒しで済ませる。scikit-robot 側の `JaxlsSolver` は
コンパイル済み問題を腕ごと(`collision_link_list` が変わるため l/r で
構造が異なる)に別々のキャッシュとして保持するため、この事前ウォームアップ
で両腕分がキャッシュされた状態になり、以後 ARMED のたびに差し出し手の
左右が入れ替わっても再コンパイルは起きない。

ただし通常運用では pre-touch/線形補間だけで事後検証に通ることが多く、
その場合は jaxls 自体が呼ばれない(`plan_handshake_motion.py` の
`--force-optimize` を付けると常に jaxls まで実行させられる。単独で
jaxls の計算時間を計測したいベンチマーク用のオプション)。

## 3. コンパイル時間の内訳(トレース/XLAコンパイル/実行)

2026-09-14 の調査(`scratch/verify_aot_split.py`。jaxls 内部の
`NonlinearSolver.solve`(`@jdc.jit` = `jax.jit` のラッパー)を
`.lower()`/`.compile()`/実行の 3 段階に分離して計測)で、軌道最適化 1 回
分(左腕)の内訳が判明した:

| フェーズ | コールド(ディスクキャッシュ無) | ヒット(ディスクキャッシュ有) |
|---|---|---|
| lower(Python側のトレース、計算グラフ構築) | 6.3〜7.7秒 | 6.3秒 |
| compile(XLAコンパイル) | 29.5秒(コード生成) | 3.0秒(キャッシュからの読み込み) |
| execute(LM反復の実行、初回呼び出し) | 0.44秒 | 0.37秒 |
| 合計 | 37.7秒 | 9.7秒 |

実測合計は実ノード(roscore + rosbag 再生、9 回連続起動)の実測値
(cold 34.9秒/36.9秒、hit 平均 左12.81秒/右11.20秒)とほぼ一致する
(IK フェーズ分を加えると `plan_person_motion` 全体で左腕 12.29 秒程度)。

重要な点:

- **「実行(LM反復そのもの)」は全体の 1〜4% しか占めない。** cold-hit の
  差(約 28 秒)の正体はほぼ全て XLA コンパイル自体(コード生成 vs
  キャッシュ読み込みの差)であり、実行コストではない。
- **`lower`(トレース)はディスクキャッシュの対象外。** `.lower()` は
  XLA に渡す前段階で Python 側の計算グラフ(jaxpr)を構築するステップで、
  jax_compilation_cache のキー生成より前の処理のため、ディスクキャッシュ
  がどれだけ効いていても毎回 6〜8 秒かかる。ヒット時の合計 9.7 秒のうち
  6 割以上をこの `lower` が占める。
- したがって、ヒット時でもコンパイルまわりだけで(`lower` 6.3秒 +
  `compile` 3.0秒 =)9.3 秒程度かかるのは仕様であり、「キャッシュが効いて
  いれば速いはず」という直感には反する。キャッシュが短縮するのは
  `compile` のみ。

## 4. 既知だったキャッシュミスの原因と対策(解決済み)

過去に 2 種類のキャッシュミス問題があり、いずれも「jaxls が計算グラフに
焼き込む FK 由来の定数が実行ごとに微妙にブレる」ことが原因だった
(scikit-robot fork `base_limit` ブランチ)。

1. **軌道最適化(`jit_solve`)側**: `_warmup_ik` の乱数シード未固定により
   IK の解自体が毎回わずかに違い、さらに skrobot が関節角を差分回転で
   適用するため下位ビットのブレが後続の腕に伝播していた。対策は
   (a) warmup 中だけ `np.random.seed` を固定、
   (b) `jaxls_solver.py` に `_quantize_fk_constants` を追加し FK 定数を
   小数 9 桁に丸めたうえで `+0.0` して負ゼロ(`-0.0`)を正規化
   (`np.round` は符号を保持するため、丸めても `-0.0` が残ると別定数として
   扱われフィンガープリントが変わってしまう)。
   → warmup 全体 47〜75秒 → 約23秒(commit `92bcc65` ほか)。
2. **バッチ IK(`jit_solve_batch`)側**: 上記の丸め処理が
   `differentiable.py`(`extract_fk_parameters`/干渉球中心座標の計算)には
   適用されていなかった。同じロジックを追加。
   → 右腕 IK 6.9〜7.2秒(常時ミス)→ 2回目以降 1.8秒(ヒット)
   (commit `3ed6358`)。

「l/r 腕の非対称性」に見えていたものはどちらも手の左右差ではなく
**「2 本目に処理される方の腕」で起きる現象**だった(`--arm rl` で順序を
入れ替えると再現先も入れ替わることを確認済み)。

## 5. 未解決の残課題(2026-09-15 追記: 11. 参照。SIGKILL 起因の疑いが強い)

左腕(1 本目)の**軌道最適化**が、実ノードで**低頻度(8〜9 回に 1 回程度)
の intermittent cache miss** を起こすことがある(2026-09-14 時点、原因
未確定・優先度低で保留)。入力姿勢(`angle_vector`/`worldpos`/`worldrot`)
は miss した回とヒットした回で bit 完全一致することを確認済みなので、
原因は FK 計算そのものの中(numpy 演算のスレッド非決定性など、量子化 9 桁
丸めの境界にたまたま乗る値がある、等)にあると推測されるが未確定。次に
調べるなら `scratch/warmup_fk_dump.py` + `scratch/compare_fk_dump.py` で
miss 時とヒット時の量子化後 FK 定数そのものを比較するのが次の一手。

2026-09-15 の実ノード再検証(8. 参照)では、8 回中 3 回で miss が発生し
(発生率としては 8〜9 回に 1 回よりかなり高い)、しかも miss したのは
右腕(2 本目)単独が 2 回、左右同時が 1 回で、**左腕単独の miss は一度も
発生しなかった**。「1 本目固定」という前提とは一致しない結果であり、
サンプル数が 8 回と少なく偶然の可能性もある一方、その再検証では毎回
`SIGINT` → 2 秒待ち → `SIGKILL` でノードを強制終了しており、jax の
ディスクキャッシュへの書き込みが完了する前にプロセスが死ぬと次回の
当該エントリが不完全になり見かけ上の miss を誘発する可能性がある
(強制終了に伴う人為的なノイズの可能性を排除できていない)。実運用に
近い「自然な起動・終了」での頻度は未確認のまま。

## 6. AOT (`jax.jit(...).lower().compile()`) について分かったこと

「warmup が実行結果を使い捨てているなら、`.lower().compile()` で
コンパイルだけ済ませて実行(execute)を省略すれば速くなるのでは」という
仮説を検証したが、**「3. コンパイル時間の内訳」の通り execute は全体の
1〜4% しかないため、効果はほぼ無い**(左腕で 0.4 秒程度の節約に留まる)。
一方で warmup が持っていた「ダミー目標が本当に解けるか」の実行時検証を
失うデメリットの方が大きいため、本番コードへの導入は見送った。

技術的な副次知見(将来 jaxls 内部を直接いじる際の参考):

- このリポジトリの venv は Python 3.11 のため、jaxls は PEP 695 の
  generics 構文(`class Foo[*Args]:`)を使わない互換モジュール
  `jaxls._py310._problem`/`jaxls._py310._solvers` を実際には使っている
  (`jaxls/__init__.py` が `sys.version_info` で分岐している)。
  `jaxls._problem` を直接 import すると `SyntaxError` になるので注意。
- `@jdc.jit`(= `jax.jit` の薄いラッパー)でデコレートしたインスタンス
  メソッドは、通常の呼び出し(`instance.method(...)`)は自動で `self` が
  bind されるが、**`.lower()`/`.compile()` にアクセスすると binding が
  外れる**。`instance.method.lower(instance, ...)` のように `self` を
  明示的に渡す必要がある(渡さないと `missing 1 required positional
  argument: 'self' 相当` のエラーになる)。
- `jdc.Static[...]` でマークした static 引数(例: `return_summary`)は
  `.lower()` 時には渡すが、コンパイル済み関数 `compiled(...)` を呼ぶ際に
  **再度渡してはいけない**(渡すと `Function compiled with input pytree
  does not match the input pytree it was called with` エラーになる。
  static 引数は既に compile 時点で計算グラフに焼き込まれているため)。
- compile-only 経路(`.compile()` のみ、実行なし)と通常の `solve()`
  実行経路は、**同じキャッシュキーに書き込まれる**ことを実測で確認済み
  (別プロセスでプロセス A が compile-only、プロセス B が通常経路を実行し、
  B 側で新規キャッシュ書き込みがゼロであることを確認)。

検証に使ったスクリプトは `scratch/verify_aot_split.py`(untracked)。

## 7. デバッグ手法

- **コンパイルが実際に走ったかどうかはログの秒数ではなく
  `~/.cache/jax_compilation_cache` のファイル数の増減で判定する。**
  `JAX_LOG_COMPILES=1`/`JAX_EXPLAIN_CACHE_MISSES=1` は `jit_solve` に
  ついては何も出力しないため当てにならない。
- 犯人(どの定数がブレているか)を特定するには `XLA_FLAGS=--xla_dump_to=DIR`
  を付けて `*.jit_solve.before_optimizations.txt`(コンパイルした時だけ
  出力される、コンパイル前 HLO)を 2 回分取得して diff する。
  `JAX_COMPILATION_CACHE_DIR` を実行ごとに空ディレクトリにすれば必ず
  コンパイルさせられる。
- HLO の diff よりも先に、jaxls へ渡す**入力側**(FK パラメータそのもの)
  を diff する方が早い。`scratch/warmup_fk_dump.py` が
  `phm.build_problem` をラップして焼き込まれる定数を npz に保存し、
  `scratch/compare_fk_dump.py` で 2 つの npz の最大絶対差・符号付き ULP
  差を出せる。
- GPU 版 jax は起動時にデバイスメモリの確保を試み、大きいサイズから
  確保に失敗するたびに `RESOURCE_EXHAUSTED: CUDA_ERROR_OUT_OF_MEMORY` の
  警告を出しながら要求サイズを段階的に縮小していくことがある(これ自体は
  正常動作で、キャッシュとは無関係)。気になる場合は
  `XLA_PYTHON_CLIENT_PREALLOCATE=false` や `XLA_PYTHON_CLIENT_MEM_FRACTION`
  で確保量を抑えられる。

## 8. `--bag` 起動時のデッドロック(未修正、2026-09-15 判明)

`run_camera_pipeline_test.py --bag <file>` は、`rospy.set_param
('/use_sim_time', True)` → `rospy.init_node` → `HandshakePipelineNode(args)`
(実機接続 `AeroROSRobotInterface` を含む `__init__` 一式)が**完了してから**
`rosbag play --clock` をサブプロセスとして起動する実装になっている。その
ため `use_sim_time=True` かつ `/clock` が一切配信されていない状態で
`__init__` 内の TF 待ち等に入り、`/clock` の最初の 1 メッセージが来ないため
**起動が永久にデッドロックする**(実機コントローラの無い開発環境で発生を
確認)。

回避策: `rosbag play <bag> --clock`(必要なら `-r`/`--loop` も)を**先に別
プロセスとして起動して `/clock` を配信させておいてから**、ノードは
`--bag` を付けずに起動する(記録済みクリップの color/depth/camera_info/
tf/tf_static は既定のトピック名と一致するため、`--bag` なしでもそのまま
subscribe される)。

```bash
rosparam set /use_sim_time true
rosbag play data/session1.bag --clock &
python3 scripts/ros/run_camera_pipeline_test.py --auto-arm --no-wait-for-client
```

本体コード(`--bag` 実装)の恒久修正はまだ行っていない(rosbag play の
起動を `rospy.init_node` の直後・`HandshakePipelineNode` 構築の前に
前倒しすれば解消するはず)。

## 9. 実ノードでの warmup 再検証(2026-09-15)

未解明のまま残っている。

## 10. 次の調査者への引き継ぎ: miss 原因のさらなる切り分け(未着手)

9. の再検証で miss 率(8 回中 3 回)が過去の記録(8〜9 回に 1 回)より
明らかに高く、しかも miss した腕が過去の記録(左腕/1 本目)と今回
(右腕/2 本目寄り)で食い違っている。原因を切り分けないまま「高頻度化
した」と結論づけるのは早計なので、以下の仮説を潰す作業を引き継ぐ。

### 仮説

1. **H1: 強制終了(SIGKILL)によるテスト起因のノイズ。** 9. のベンチは
   毎回 `_warmup_ik_body` 完了を検知した直後に `SIGINT` → 2 秒 →
   `SIGKILL` でノードを終了させている。jax の永続コンパイルキャッシュ
   (特に `xla_gpu_per_fusion_autotune_cache_dir` 配下の autotune 結果)
   の書き込みが `plan_person_motion()` の呼び出し復帰後も非同期に続いて
   いる場合、次回起動時にそのエントリが不完全な状態で読まれて検証に失敗
   し、見かけ上の miss として観測される可能性がある。
   - **切り分け方**: ノードを `SIGKILL` せず、`_warmup_ik_body` 完了後に
     十分な待ち時間(例: 10〜30 秒)を置いてから `SIGINT` のみで終了させ、
     プロセスが完全に終了する(`kill -0` が失敗する)まで待ってから次の
     反復を開始するように `bash /tmp/warmup_bench/bench_all.sh` 相当の
     スクリプトを書き直し、同じ 8 回(できれば 15〜20 回に増やしてサンプル
     数を稼ぐ)を再実行する。miss 率が 8〜9 回に 1 回程度まで下がれば H1
     が濃厚。
   - 併せて、各反復の直前直後で `find ~/.cache/jax_compilation_cache
     -newer <直前のタイムスタンプファイル>` 相当のコマンドで新規/更新
     ファイルを記録し、miss した反復の**直前**の反復で当該キャッシュ
     ファイルが本当に更新されていたか(≒ 書き込みが SIGKILL 前に完了して
     いたか)を確認する。

2. **H2: 「2 本目に処理される腕」で起きる一般現象(section 4 で解決済みの
   ものと同種・未解決版)。** `_warmup_ik_body`(scripts/ros/
   run_camera_pipeline_test.py:737)は常に `('l', 'r')` の順で処理する
   ため、warmup の文脈では「2 本目」は常に右腕になる。9. の結果(右腕
   偏りの miss)はこれと整合する一方、section 5 が引用する過去の記録
   (「左腕(1 本目)が…」)は**別のスクリプト/別の腕順**での観測だった
   可能性があり、本当は「1 本目 vs 2 本目」ではなく「2 本目」で一貫して
   いたのかもしれない。
   - **切り分け方**: `_warmup_ik_body` の `for robot_arm, label in
     (('l', '右'), ...)` の順序を一時的に `('r', 'l')` に入れ替えた
     ローカルパッチ(本番コードには戻す)で同じベンチを回し、miss が
     「常に右腕」から「常に左腕(=今度は 2 本目になった方)」に追従する
     か確認する。追従すれば「2 本目固有の現象」で確定し、過去の「左腕
     (1 本目)」という記述自体を section 5 で訂正する。

3. **H3: この環境(RTX 5090、ドライバ 576.88)固有の autotune キャッシュ
   未成熟。** 5090 は新しい GPU アーキテクチャで、`~/.cache/

   fusion 形状だけ毎回作り直し(もしくは autotune 自体が非決定的で
   毎回微妙に違う結果を選び、それが後段の FK 定数のブレに波及)している

   - **切り分け方**: miss した反復の HLO ダンプ(`XLA_FLAGS=
     --xla_dump_to=DIR`、既存の「7. デバッグ手法」参照)を hit した反復

     あるか(≒ 入力側の FK 定数がブレている、H2/既存の量子化問題と同種)
     か、それとも `before_optimizations.txt` は同一なのに autotune 選択
     (実行プランの中身)だけが違うか、を切り分ける。後者であれば H3 が
     濃厚。

## 11. H1(SIGKILL によるキャッシュ書き込み未完了)の検証結果(2026-09-15、解決)

10. の H1 仮説(「毎回 `SIGINT` → 2 秒待ち → `SIGKILL` で強制終了して
いたため、jax の永続コンパイルキャッシュへの非同期書き込みが完了する前に
プロセスが死に、次回起動時に不完全なエントリを読んで見かけ上の miss を
誘発していたのではないか」)を検証した。

### 検証方法

`scratch/bench_h1.sh`(untracked、H1 切り分け用に `scratch/run_warmup_repeat.sh`
相当の既存ベンチから複製・改変)で、9. のベンチとの差分として:

- `SIGKILL` を撤廃し、`_warmup_ik_body` 完了検知後に **20 秒待ってから
  `SIGINT` のみ**でノードを終了。
- プロセスが自発的に終了する(`kill -0` が失敗する)まで最大 60 秒待って
  から次の反復に進む(60 秒超えたら `SIGKILL` にフォールバックする安全弁
  のみ残したが、今回の 16 回では一度も発動しなかった)。
- 各反復の直前直後で `find ~/.cache/jax_compilation_cache -newer <前回の
  タイムスタンプファイル>` により新規/更新されたキャッシュファイル数を記録。

`roscore` + `rosbag play data/session1.bag --clock`(ループなし、毎回新規
起動しなおす)+ `run_camera_pipeline_test.py --auto-arm
--no-wait-for-client` を **16 回連続起動**(9. の 8 回から増やしてサンプル
数を稼いだ)。

### 結果

| 指標 | 9. (SIGKILL あり、8 回) | 11. (SIGINT のみ、16 回) |
|---|---|---|
| miss 回数 | 3/8 (右腕 2 回、左右同時 1 回) | **0/16** |
| 新規/更新キャッシュファイル数(2 回目以降) | (未計測) | **常に 0**(1 回目のみ 7480) |

16 回全てで左右両腕とも hit し(左腕 軌道最適化 11.9〜13.3 秒、右腕
10.7〜13.9 秒、いずれも「3./9. 節」の hit 実測レンジと一致)、
2 回目以降のキャッシュディレクトリへの新規/更新ファイルは一度も検出
されなかった(= 1 回目の起動で書き込まれたキャッシュが 2 回目以降
すべてそのまま読まれ続けた)。これは 9. で観測された「8 回中 3 回 miss」
という高頻度化が **ベンチの終了方法(SIGKILL による強制終了)自体が
誘発した人為的なノイズだった**ことを強く裏付ける結果であり、H1 が主因
と結論づける。

### 結論・今後の方針

- **「実運用(自然な起動・終了)での miss 率」は、少なくとも今回の
  16 回の範囲では 0 回だった。** 5. で記録されていた「8〜9 回に 1 回」
  という過去の頻度自体も、当時の終了手順(ベンチ/デバッグ時の強制終了、
  もしくは開発中の Ctrl-C 連打など)に起因していた可能性が高く、
  **「軌道最適化側の量子化 FK 定数がなお微妙にブレる」という別のバグが
  実在するとは言い切れなくなった**(4. で解決したはずの現象の再発では
  なく、そもそも今回はそのクラスの miss を一度も観測していない)。
- H2(2 本目の腕で起きる現象)・H3(RTX 5090 の autotune 未成熟)は、
  miss 自体が SIGKILL なしでは発生しなかったため、**今回は検証不要と
  判断し保留のままとする**(将来 miss が再発した場合に切り分ける)。
- 実運用上の対策: ノード終了時に `SIGKILL` を使う運用(手動の Ctrl-C
  連打や、外部からの強制終了スクリプト)は、次回起動時の再コンパイル
  (腕あたり 20〜30 秒)を誘発しうるため避け、**`SIGINT` を送った後は
  プロセスが自発的に終了するまで待つ**(rospy のシグナルハンドラが
  正常系の shutdown 処理を完走できるようにする)運用を推奨する。
  本体コード側での対策(例: シグナルハンドラ内でキャッシュ書き込み完了を
  待つ、等)は現時点では不要と判断する(そもそも `SIGINT` だけで正常終了
  できているため)。
- 5. の記述はこの結果を踏まえて「未解決」から「SIGKILL 起因の疑いが強い
  (2026-09-15 時点、自然終了では 16 回中 0 回)」に読み替えること。

検証に使ったスクリプトは `scratch/bench_h1.sh`(untracked)。

## 12. 最終確認(2026-09-15): 実ノード1人分 + オフラインパイプラインの計測、および `solve_palm_ik.py` へのウォームアップ導入

11. の結論を踏まえ、実運用に近い形で最終確認を行った。

### `run_camera_pipeline_test.py`(実ノード、`--auto-arm`、rosbag 1 人分、
自然終了)

warmup(両腕とも hit):

| | IK | 軌道最適化 (jaxls) |
|---|---|---|
| 左腕 | 2.7 秒 | 11.9 秒 |
| 右腕 | 1.7 秒 | 10.9 秒 |

本番(warmup 後、rosbag 中の 1 人を検出して解いた実測。この人物は
pre-touch 経由の幾何的な軌道が事後検証に通ったため jaxls 本体は呼ばれて

- IK: `collision_ik_time` 0.19 秒 + `candidate_selection_time` 0.06 秒

- 軌道計画: `compute_time` 0.86 秒 (`kind: pretouch`)

warmup を経ているため、本番の処理は「3. コンパイル時間の内訳」でいう
`execute` 相当のコストしか払っておらず、11. で確認した「SIGKILL さえ
避ければ安定して hit する」という結論とも整合する結果になった。

### `run_pipeline_test.py`(オフラインのパイプライン回帰テスト、
`--plan-motion`)

このスクリプトは `run_camera_pipeline_test.py` の `_warmup_ik` に相当する

ため 20 人生成し、対象になった 3 人で「1 人あたり平均計算時間」を計測
した。

**ウォームアップ導入前**(3 人の平均。1 人目が jit のトレース/コンパイル
コストをそのまま被り、2 人目以降は同一プロセス内の trace 再利用で速い
ため、平均としては両者が混ざった値になる):

| 段階 | 1 人あたり平均 |
|---|---|
| 掌推定 | 0.004 秒 |
| IK 1段階目 (干渉回避バッチIK、`jit_solve_batch`) | **2.673 秒** |
| IK 2段階目 (事後の干渉検証+後処理判定) | 0.338 秒 |
| 軌道計画 (jaxls、3 人とも `force_optimize` なしで pre-touch/線形補間の

### 導入した対策: `solve_palm_ik.py` にバッチIKのウォームアップを追加

`run_camera_pipeline_test.py` の `_warmup_ik`(ダミー目標で両腕を 1 回ずつ
事前に解いておき、jit のトレース/コンパイルをノード起動時に前倒しする
手法)のうち、**バッチIK (`solve_person_ik` → `batch_inverse_kinematics`,
`backend='jax'`) の部分は `solve_palm_ik.py` にもそのまま適用できる**と
判断し、`_warmup_batch_ik`(`solve_palm_ik.py`)として実装した
(`main()` が人物ループに入る前、`--no-warmup` で無効化可能。既定で有効)。

適用できると判断した理由: バッチIKは `run_camera_pipeline_test.py` の
本番運用と同様、**IK 対象になった人物には必ず (毎回) 実行される**処理
だから。`--robot-arm auto`(既定)のときは対象人物がどちらの手を差し出す
か事前に分からないため、`_warmup_ik` と同じく両腕分ウォームアップする
(`--robot-arm` で腕を固定している場合は使う方だけ)。ダミー目標には
`human_body_obstacles({})` (骨格なしの固定長ダミー障害物、`_warmup_ik`
と同じ)を使い、実際の対象者と同じ shape で jit をトレース/コンパイル
させる。

**効果**(同じ `--seed 42`、20 人生成・3 人が対象、条件は導入前と同一):

| 段階 | 導入前 | 導入後 |
|---|---|---|
| IK 1段階目 (バッチIK) | 2.673 秒/人 | **0.142 秒/人** (約19倍) |
| IK 2段階目 | 0.338 秒/人 | 0.485 秒/人 (誤差範囲、後述) |
| 掌推定込み全体 | 3.015 秒/人 | 0.632 秒/人 |

IK 2段階目 (`pick_verified_candidate` の後処理判定) が誤差範囲で変わって
いるのは、`solve_palm_ik.py` はこのスクリプト自身には `--seed` を渡して
いない (`run_pipeline_test.py` の `--seed` は `generate_random_human_
poses.py` にしか渡らない) ため、バッチIKの初期値サンプリングが実行の
たびに変わり、採用される候補・試行回数が変動することによる自然なばら
つきであり、ウォームアップとは無関係。

### `plan_handshake_motion.py` へは移植しなかった (jaxls 軌道最適化の
ウォームアップは見送り)

`_warmup_ik` のもう一方の要素 (jaxls の軌道最適化を事前に 1 回解いて
おく) は、**このスクリプトには移植しなかった**。理由:

- `run_camera_pipeline_test.py` はノードが起動している間ずっと動き続け、
  ARMED になるたびに(高い確率で)軌道計画が要求されるため、起動時に
  1 回だけ前倒しコストを払う価値がある。
- 一方 `plan_handshake_motion.py`/`run_pipeline_test.py` は**1 回の
  起動につき 1 回だけ**実行される使い捨てプロセスで、しかも
  `plan_person_motion` は pre-touch/線形補間の幾何的な軌道が事後検証を
  通ればそこで早期 return し jaxls 自体を呼ばない(`--force-optimize`
  を付けない限り、実測でも 3 人中 3 人とも jaxls 未使用で verified に
  到達した)。jaxls が全く必要ない実行でも一律にウォームアップすると、
  ヒットしていてもなお数秒〜十数秒 (`lower` 6〜8 秒 + `compile` 数秒、
  「3. コンパイル時間の内訳」参照) を毎回無条件に追加するだけになり、
  このスクリプトの典型的な使われ方 (変更のたびに素早く回す回帰テスト)
  にとってはむしろ悪化になる。
- そのため、jaxls が実際に必要になった人物が最初に払うコストは許容し、
  同一プロセス内で 2 人目以降が要る場合はその再利用(trace の使い回し)
  に任せる、という現状の挙動のままにした。

### 補足: `solve_palm_ik.py` のウォームアップも「対象 0 人なら無駄」だった
(2026-09-15 追記、対策済み)

上の説明のうち「`run_camera_pipeline_test.py` はノードが動き続けるので
起動時に前倒しする価値がある/`plan_handshake_motion.py` は使い捨て
プロセスだから見送った」という対比は、実は `solve_palm_ik.py` にも
半分だけ当てはまる。`solve_palm_ik.py` も `run_pipeline_test.py` からは
**人物全員分まとめて 1 回だけ** subprocess 起動される(人物ごとに新しい
プロセスが立つわけではない。他の 3 ステップ (`generate_random_human_
poses.py`/`estimate_palm_poses.py`/`plan_handshake_motion.py`) も同様)。

ウォームアップの効果を正しく整理すると:

- **バッチ内に IK 対象が 1 人以上いる場合**: トレース/コンパイルの
  コストはウォームアップの有無に関わらずそのプロセス内で結局 1 回は
  払うことになるため、**プロセス全体の壁時計時間はほぼ変わらない**
  (1 人目が払うか、ウォームアップが先に払うかの違いだけ)。ウォーム
  アップの実質的な効果は、「1 人あたり平均計算時間」(`run_pipeline_
  test.py` が表示する指標) が 1 人目の cold なコストに引きずられず、
  定常状態 (hit) の値を反映するようになることであり、これは実際に
  2.673 秒/人 → 0.142 秒/人 という形で確認できた。
- **バッチ内に IK 対象が 1 人もいない場合**: バッチIK
  (`batch_inverse_kinematics`) はそもそも 1 回も呼ばれないため、
  ウォームアップは完全に無駄(2〜9 秒程度)になる。今回の実測でも
  20 人中 17 人が対象外、単発の 1 人入力では 10 seed 中 10 回とも対象外
  だったことを踏まえると、この「対象 0 人」のケースは珍しくない。

これは `plan_handshake_motion.py` を見送った理由(「使われない実行でも
一律にコストを払うのは損」)と本質的に同じ問題であり、`solve_palm_ik.py`
側の説明が一貫していなかった。そのため、**`main()` でループに入る前に
入力ファイル群に IK 対象 (`offered_hand` が L/R) が 1 人でもいるかを
先に確認し、1 人もいなければウォームアップ自体をスキップする**よう
`solve_palm_ik.py` を修正した(`--no-warmup` の指定に関わらず、対象 0 人
なら実行されない)。動作確認(実ノードは使わずオフラインで):

- 対象 1 人のバッチ: `[warmup] l腕: ... 1.8 秒` / `[warmup] r腕: ... 5.9
  秒` が出力され、その 1 人の処理は速い。
- 対象 0 人のバッチ (3 人生成、全員 `offered_hand: null`): `[warmup]`
  行が一切出力されず、即座に完了。
